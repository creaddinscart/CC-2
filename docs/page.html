Getting started

  1. Download CC-2.0.zip ({{RELEASE_SIZE}}). It is the only download on this page.
  2. Unzip the whole folder anywhere. Keep the files together.
  3. Open the launcher for your system, then pick 1 Terminal UI in the menu.

How it works

Creating a room starts a temporary server on the host's machine. The server only forwards ciphertext.

Your terminal

curses client, local key derivation, file picker.

  • Password never leaves the client
  • Key from password + room salt
  • Plaintext stays in RAM
Temporary room server

Bound to your chosen port. Stops when the room closes.

  • Sees ciphertext, usernames, timestamps
  • Stores a separate auth verifier
  • Cannot recover the message key
  • Cannot read text or files
Peer terminals

Connect by IP + port, probe, then unlock with the password.

  • IPv6 preferred
  • FRP exit when NAT blocks inbound
  • History replayed as ciphertext

Trust model. The password is the only key source and must be shared out of band. If any member lacks the optional cryptography package, the whole room falls back to the built-in HMAC-CTR cipher.

  1. Choose a username

    On first run, pick a username. It is saved in ~/.cc2/config.json. The menu also has a Change Username button.

  2. Host: create a room

    Enter room name, port, communication IP, password and maximum members. IPv6 global is preferred; the transport list is auto-detected. Behind NAT, click FRP Exit to publish a public address. Creating the room starts the temporary server and opens chat.

    Name night-shiftPort 7777Cap 8

  3. Guest: check the room

    Enter the host's IP + port (or the FRP server address + remote port) and click Check Room. The room replies with its name, host, member count and capacity. Only then is the password requested.

  4. Chat and send files

    Type and press ENTER. Peers see who is typing. Click File to open the picker; files are encrypted, chunked and reassembled into ~/Downloads/CC-2.0/. TAB, arrows, ENTER and ESC work as keyboard alternatives.

  5. Host: tune the room

    Change the member cap at any time, kick a member, or close the room. Closing stops the temporary server.

Transports

  1. IPv6 globalpreferred
    Used first when available. Direct reachability without NAT.
  2. Public IPv4 / WANfallback
    Chosen when no global IPv6 exists. Usually needs port forwarding and an open firewall port.
  3. VPN / Radmin VPNvirtual lan
    All peers join the same virtual network. Radmin ranges (26.0.0.0/8) are detected automatically.
  4. LANlocal network
    Same Wi-Fi or Ethernet. Simplest for one building.
  5. Loopbacklocal testing
    127.0.0.1 / ::1 for a single-machine test with two terminals.

If a peer cannot connect: check the firewall, port forwarding, VPN membership and the advertised IP. Use python3 cc2_server.py --list-addresses to see what the host detects. With no reachable address at all, use an FRP exit.

FRP exit

No public IP or stuck behind CGNAT? Set it up exactly like a Minecraft server: download a third-party FRP client, map a public port to the room's local port, and start it. CC-2.0 does not install, configure or run frpc - it only needs the public host:port that guests connect to.

topology
guest --> frps:25565 == tunnel ==> frpc --> 127.0.0.1:9001 (room)
  1. In your own FRP client, add a plain tcp proxy. Set localPort to the CC-2.0 room port and remotePort to the public port you will share. The two can differ.
  2. Start frpc and keep it running. Its server address, control port, token and proxy name stay in your FRP client - CC-2.0 never asks for them and writes no config files.
  3. In CC-2.0 open Main menu / FRP Exit (or the FRP Exit button on the Create Room form) and enter one address: frp.example.com:25565. Switch FRP on and click Save.
  4. Guests enter that host + port, click Check Room, then enter the password. They need no FRP software and never see your local port.
frpc.toml in your own FRP client
serverAddr = "frp.example.com"
serverPort = 7000

[[proxies]]
name = "cc2"
type = "tcp"
localIP = "127.0.0.1"
localPort = 9001
remotePort = 25565
headless host
$ python3 cc2_server.py --name "Night Shift" --port 9001 --password 'long-password' --frp frp.example.com:25565

Note. This is the same mapping you would use for a Minecraft server on 25565. Keep frpc running and open the remote port on the FRP server firewall. Use a plain tcp proxy: the FRP PROXY protocol prepends bytes that break CC-2.0 framing. In FRP rooms host rights require the admin token printed by the headless server; paste it into the Admin token field on the Join Room form. The FRP server only relays ciphertext, never the password or the key.

Troubleshooting

  • Cramped terminal - enlarge the window; the layout adapts from 80 columns.
  • Mouse does nothing - enable X10 mouse reporting, or use TAB / arrows / ENTER.
  • Windows curses error - install windows-curses.
  • Old messages unreadable - a new password makes a new key; cached history is skipped.
  • No AES-GCM - the room falls back to HMAC-CTR automatically.
  • FRP exit silent - start frpc, open the remote port, keep localPort equal to the room port.
  • FRP probe malformed - disable the FRP PROXY protocol on that proxy.

Security

  • The password is never transmitted; the server stores only a separate auth verifier.
  • Usernames, member counts and timestamps are visible to the server.
  • No forward secrecy, no identity check beyond the shared password.
  • Share the password over a different channel than the address.
  • Closing the room stops the server and drops in-memory state.
  • An FRP server relays ciphertext only. It cannot read messages or files.
  • FRP rooms require the admin token for host rights.
